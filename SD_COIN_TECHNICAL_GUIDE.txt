SD COIN WEBSITE — COMPLETE TECHNICAL AND SETUP GUIDE
====================================================

1. WHAT THIS WEBSITE IS
-----------------------
SD Coin is a private, centralized demo wallet website. Members can register,
log in, view an internal SD balance, transfer SD to another member, inspect
transaction history, and voluntarily mine demo blocks using a browser-based
SHA-256 proof-of-work puzzle.

Important: SD is an internal database balance in this project. It is not
Bitcoin, not a decentralized cryptocurrency, not a bank deposit, and has no
cash value. The Render backend and its database control the account balances
and the single shared chain.

2. TECHNOLOGIES USED
--------------------
FRONTEND
- HTML5: page structure and forms.
- CSS3: responsive layout and visual design.
- JavaScript (ES2020+): API calls, wallet display, mining loop, presence
  heartbeat, and client-side SHA-256 through the browser Web Crypto API.
- GitHub Pages: static website hosting.

BACKEND
- Python 3.10+: server programming language.
- Flask: REST API and request routing.
- Flask-CORS: allow only configured frontend website origins.
- Flask-SQLAlchemy / SQLAlchemy: database models and queries.
- Werkzeug security: salted password hashing and password verification.
- itsdangerous: signed, time-limited login tokens.
- Flask-Limiter: rate limiting for public endpoints.
- Gunicorn: production WSGI server on Render.

DATABASE
- SQLite for local development.
- PostgreSQL for hosted deployment.

CRYPTOGRAPHY / HASHING
- SHA-256: proof-of-work hash for blocks and integrity checks.
- Werkzeug password hashing: one-way salted password hashes for passwords.
- Signed authentication token: detects token tampering and expires after
  two hours. It is not a replacement for HTTPS.

4. HOW THE WEBSITE WORKS
------------------------
1. The browser loads static HTML, CSS and JavaScript from GitHub Pages.
2. frontend/config.js contains the HTTPS URL of the Flask backend.
3. JavaScript sends JSON requests to the backend using fetch().
4. The backend validates each request and checks the signed login token.
5. SQLAlchemy reads or updates PostgreSQL (or local SQLite).
6. The backend returns JSON; the browser updates the page.
7. CORS permits requests only from the origin(s) configured in
   FRONTEND_ORIGINS. CORS is not authentication; token checks are separate.

5. ACCOUNT AND PASSWORD SECURITY
--------------------------------
- New passwords must be 12–128 characters. Prefer a long unique passphrase.
- Passwords are stored as salted one-way password hashes. The plain password
  is not written to the user table.
- Never send a password to anyone, put it in this guide, commit it to GitHub,
  or put it in frontend JavaScript.
- Login tokens expire after two hours.
- The account auth-version number is included in each token. Changing the
  password or using Log out increments that version and invalidates tokens
  from all logged-in devices. Users must log in again afterwards.
- Login is rate limited to reduce password guessing. Registration is also
  rate limited. The default rate-limit store is process memory for this demo.
  For a production/multi-worker deployment, provision private Redis and set
  RATELIMIT_STORAGE_URI to its private connection URL. Do not expose Redis.
- HTTPS is required for the live site. Never deploy with an HTTP API URL.
- API responses include security headers, API responses are not cached, JSON
  request bodies are size-limited, and CORS is restricted to allowed origins.
- Admin credentials are supplied only as Render environment variables.

Security limitations that still need professional work before a public launch:
- Add verified-email registration and a secure email password-reset process.
- Consider MFA for members and require MFA for administrators.
- Use Redis-backed rate limiting and monitoring in production.
- Add security alerts, audit review, backups, restore tests and incident plans.
- Have the code independently reviewed and penetration-tested.
- Review applicable privacy, consumer, financial and crypto regulations before
  offering anything that could be mistaken for redeemable or purchasable value.

6. PRIVACY AND ONLINE DEVICE PRESENCE
------------------------------------
When a signed-in user opens the dashboard, the browser creates a random device
session identifier and sends a heartbeat about every 30 seconds. The server
stores only:
- the account's User ID;
- a random browser-generated device session ID;
- a broad label: Mobile or Desktop;
- the last-seen timestamp.

The presence feature does not request GPS, contacts, camera, microphone,
photos, phone number, hardware serial number, or a full browser user-agent.
Stale device records are deleted after approximately three minutes. The
online-device count is visible only to the signed-in account itself. This is
an activity indicator, not proof that a person is physically using the device.

The browser keeps the short-lived auth token in sessionStorage rather than localStorage. This reduces persistence after the tab/session ends, but JavaScript running in the page can still access it; preventing cross-site scripting remains important.

The project still stores account name, email, password hash, balance,
transactions and mining block metadata in its database. The admin/operator
who controls the backend and database can access stored account information.
Do not collect information you do not need. Publish a privacy notice that
matches your real hosting, retention, support and deletion practices. This
starter does not yet provide a self-service account deletion feature.

7. HOW MULTI-DEVICE MINING WORKS
-------------------------------
- The user must sign in on each device (for example, a mobile phone and laptop).
- The user must press Start Mining separately on each device. No device starts
  mining automatically and the site does not remotely activate a device.
- The server assigns each browser session a separate nonce search region.
  This reduces duplicate hashing when two devices mine the same account.
- Each device repeatedly hashes a block candidate with SHA-256 until it finds
  a hash beginning with the configured number of zero characters.
- The browser submits the candidate proof. The backend recalculates the hash
  independently and checks the current chain tip before crediting a reward.
- The first valid submission for a block wins. If another device wins first,
  the other device receives a stale-chain response and starts on the next job.
- Each accepted block currently rewards 25 SD. Difficulty is currently three
  leading hexadecimal zeroes. These are demo settings, not a secure economic
  issuance schedule.
- Mining pauses when its browser tab becomes hidden. The user can press Stop
  at any time. A device needs to remain online with the dashboard open.

Mining consumes CPU, battery and may generate heat. Use only devices you own
or have permission to use. Do not try to bypass a browser's background limits,
run hidden miners, or install mining code on another person's device. The
browser miner is intentionally opt-in and visible to the account holder.

8. BLOCKCHAIN AND SHA-256 EXPLAINED
----------------------------------
A block stores an index, previous block hash, timestamp, miner User ID, reward,
nonce and its own hash. The hash is calculated from a fixed text representation
of those fields using SHA-256. The nonce is changed until the hash meets the
proof-of-work target. Each block points to the previous block's hash, so a
change to an earlier block makes later links fail the chain verification.

SHA-256 is a one-way hash, NOT encryption. It does not conceal the original
information and cannot be used to hide names, emails or private messages.
Never store passwords or private data in a block. If confidential data must
be stored, use authenticated encryption and keep encryption keys outside the
blockchain. This demo chain is centralized: one server/database accepts blocks
and decides the chain tip. It does not have peer-to-peer nodes, decentralized
consensus, mining pools, public network validation or cryptocurrency wallets.

9. DATABASE TABLES
------------------
users
  id, user_id, name, email, password_hash, role, balance, created_at,
  auth_version.

ledger_entry
  transaction_id, idempotency_key, sender_user_id, receiver_user_id, amount,
  kind, created_at. This records transfers, admin credits and mining rewards.

block
  block_index, previous_hash, timestamp, miner_user_id, reward, nonce,
  block_hash.

mining_device
  user_id, device_key, device_label, last_seen. Used for short-lived online
  device presence. Expired presence records are cleaned up during heartbeats.

The backend includes an additive migration for auth_version so an existing
users table can be upgraded without resetting member balances. Always take a
PostgreSQL backup before deploying schema changes.

10. API ENDPOINTS
-----------------
POST /api/register             Create an account.
POST /api/login                Sign in and receive a signed token.
GET  /api/me                   Read the signed-in user's own account summary.
POST /api/logout-all           Revoke all login tokens for the account.
POST /api/change-password      Change password and revoke old sessions.
POST /api/transfer             Transfer SD to another member.
GET  /api/transactions         Read the signed-in user's transaction history.
POST /api/presence              Update current device heartbeat and get own
                               online-device count.
GET  /api/mining/challenge     Get a mining challenge and device nonce range.
POST /api/mining/submit        Verify proof and attempt to credit the reward.
GET  /api/chain                Read recent blocks and verify chain links.
POST /api/admin/issue          Admin-only issuance of internal demo SD credits.

Authenticated endpoints expect:
Authorization: Bearer <signed-token>

11. DEPLOY LOCALLY
------------------
Install Python 3.10 or later. In a terminal:

  cd backend
  python -m venv .venv

Activate the virtual environment:
  Windows: .venv\Scripts\activate
  macOS/Linux: source .venv/bin/activate

Install packages:
  pip install -r requirements.txt

Set environment variables before starting. Example for macOS/Linux:
  export SECRET_KEY="a-random-secret-of-at-least-32-characters"
  export FRONTEND_ORIGINS="http://127.0.0.1:5500,http://localhost:5500"
  export ADMIN_EMAIL="your-admin-email@example.com"
  export ADMIN_PASSWORD="a-unique-admin-password-at-least-16-characters"
  python app.py

For PowerShell, use $env:NAME="value" before running python app.py.

In a second terminal:
  cd frontend
  python -m http.server 5500

Set frontend/config.js to:
  window.SD_COIN_API_URL = "http://127.0.0.1:5000";

Open http://127.0.0.1:5500 in a browser. Local HTTP is only for local testing.

12. DEPLOY TO RENDER AND GITHUB PAGES
-------------------------------------
A. Backend on Render
1. Push the project to a private or public GitHub repository. Never upload
   passwords, .env files, database backups, or SECRET_KEY values.
2. Create a PostgreSQL database on Render.
3. Create a Python web service. Set its root directory to backend if the
   backend folder is inside the repository.
4. Build command: pip install -r requirements.txt
5. Start command: gunicorn app:app
6. Set environment variables in Render:
   SECRET_KEY          Random secret with at least 32 characters.
   DATABASE_URL        Render PostgreSQL connection string.
   FRONTEND_ORIGINS    Exact GitHub Pages origin, e.g. https://account.github.io
   ADMIN_EMAIL         Admin email address.
   ADMIN_PASSWORD      Unique admin password, at least 16 characters.
   RATELIMIT_STORAGE_URI Optional private Redis URL for shared rate limits.
7. Deploy and visit the service root. It should return status online.

B. Frontend on GitHub Pages
1. Upload the contents of frontend/ to the repository root (index.html must
   be at the root of the Pages source).
2. Enable GitHub Pages in repository Settings > Pages.
3. Copy the website origin, such as https://account.github.io. If using a
   project path, the origin still excludes the repository path.
4. Add that origin to Render FRONTEND_ORIGINS and redeploy the backend.
5. Set frontend/config.js to the Render HTTPS backend URL and commit the file.
6. Open the GitHub Pages site, register or sign in, and test transfers/history.
7. Test mining on one device first. Then sign in on another device and press
   Start Mining there too. Check the online device count.
